# ADR-0003: хранение статуса и идемпотентность запросов в t-proxy-service

- Статус: принято
- Дата: 2026-11-22
- Область: `t-proxy-service` (шаги 4 и 5 плана); подход применим к другим сервисам проекта

## Контекст

Шаг 4 плана вводит БД proxy (Flyway + jOOQ, ADR-0001). До написания схемы нужно решить: чем генерировать jOOQ-классы, как хранить статус платежа и как устроить идемпотентность `POST /payments` по заголовку `Idempotency-Key` (D10). Конфликт, который пришлось разрешить: контракт D10 обещает `409` для повтора, пока первый запрос «ещё обрабатывается», а «обрабатывается» длится и после коммита транзакции (публикация в Kafka, D5).

## Решения

### 1. Генерация jOOQ (D19)

Плагин `dev.monosoul.jooq-docker` (на 2026-11-22 последняя версия 8.0.21): поднимает Postgres в Docker, применяет миграции Flyway, запускает jOOQ codegen. Запасной путь — официальный `org.jooq.jooq-codegen-gradle` с собственной задачей, поднимающей Docker и Flyway; затем DDLDatabase (ADR-0001).

Проверить при настройке: совместимость Flyway из плагина с Postgres 18; совпадение версии jOOQ у плагина с версией, которой управляет Spring Boot 4.2.

### 2. Статус платежа в БД (D20)

Столбец `status` типа `text` с ограничением `CHECK` на семь значений (`ACCEPTED`, `FUNDS_RESERVED`, `PARTNER_CONFIRMED`, `COMPENSATING`, `UNKNOWN`, `COMPLETED`, `FAILED`). В коде — enum домена; на границе адаптера значение преобразуется. Добавление статуса — миграция, меняющая `CHECK`. Аналогично `CHECK` на `service_type`, `currency`, `amount_minor > 0`.

### 3. Идемпотентность (D21)

Одно состояние, без `409`.

Таблица `idempotency_keys`: первичный ключ `(customer_id, idempotency_key)` (ключ принадлежит клиенту), `request_hash` (SHA-256 канонического тела: `accountNumber`, `serviceType`, `amountMinor`, `currency`), `payment_id`, `created_at`.

Поток запроса:
1. В одной транзакции: `INSERT` ключа с обработкой конфликта по `(customer_id, idempotency_key)` (`ON CONFLICT (customer_id, idempotency_key) DO NOTHING`; цель конфликта указывается явно, чтобы нарушение других ограничений не маскировалось под «ключ уже есть»).
2. Вставка удалась — тот же коммит записывает платёж `ACCEPTED`; после коммита синхронная публикация `PaymentRequested` (`acks=all`), затем `202` (D5).
3. Конфликт — читаем существующую запись: тот же `request_hash` → `202` с существующим платежом, событие **не** публикуется; другой `request_hash` → `422`.

Параллельные запросы с одним ключом: второй `INSERT` ждёт завершения транзакции первого (миллисекунды; публикация в Kafka идёт после коммита и блокировку не держит), затем видит конфликт и возвращает `202` с тем же платежом. Поэтому `409` и `Retry-After` для этого случая не нужны.

## Рассмотренные альтернативы

| Вопрос | Вариант | Почему не выбран |
|---|---|---|
| Идемпотентность | Два состояния (`IN_PROGRESS` → `COMPLETED`) + таймаут «брошенного» ключа | Сохраняет `409` из D10 и не отдаёт повтору `202` до подтверждения публикации, но требует состояния, перевода в `COMPLETED`, таймаута и обработки зависших ключей. Для учебного проекта лишняя сложность. **[prod-note]** в проде предпочтителен |
| Идемпотентность | Ключ без привязки к клиенту | Чужие клиенты могли бы сталкиваться на одинаковых ключах и видеть чужие платежи |
| Статус | Enum Postgres | Значения добавляются через `ALTER TYPE`, удалить нельзя; статус `COMPENSATING` появился уже в ходе проектирования |
| Codegen | Только собственная задача на официальном плагине | Больше склейки; оставлен как запасной путь |

## Последствия

- **D10 меняется:** ответ `409` и `Retry-After` для параллельного дубля убираются из контракта. Остальное из D10 сохраняется (повтор с тем же телом → `202` с тем же платежом, другое тело → `422`, сбой публикации → общий `500`). Нужно обновить `openapi.yaml` и сценарий теста шага 5: две одновременные одинаковые заявки дают два `202` с одним платежом и одним событием.
- **Слабее гарантия D5 для повторов:** повторный запрос может получить `202` до того, как первый получил подтверждение публикации. Если первый запрос упал на публикации, платёж остаётся в `ACCEPTED` без события (известная дыра D5, устраняется outbox на этапе 3), клиент проверяет статус через `GET /payments/{id}`.
- Таймауты и перевод ключей в `COMPLETED` не нужны: шаг 5 проще.
- Очистка старых ключей (TTL) не входит в шаг 4 и фиксируется как известное ограничение.
