# ADR-0002: публикация событий, топики и ключи

- Статус: принято (ключ партиционирования для `wallet.events.v1` и `partner.events.v1` подтверждается при проектировании этих сервисов)
- Дата: 2026-11-22
- Область: `t-proxy-service`; конвенции распространяются на весь проект

## Контекст

Proxy принимает платёж по REST, записывает его в Postgres и должен уведомить остальные сервисы через Kafka. Между Postgres и Kafka нет общей транзакции (dual write). Нужно также определить природу публикуемого сообщения, именование топиков и ключ партиционирования, и договориться, на что подписан proxy для обновления статуса.

## Решения

### 1. Dual write на этапе 2 (D5)

1. В одной транзакции БД записываются платёж со статусом `ACCEPTED` и ключ идемпотентности; транзакция коммитится.
2. После коммита proxy публикует `PaymentRequested` синхронно: `acks=all`, ожидание подтверждения.
3. Только после подтверждения клиент получает `202`.
4. На этапе 3 roadmap публикация заменяется на Transactional Outbox.

**Известная дыра (сознательное упрощение):** если процесс упал или Kafka недоступна после коммита, платёж остаётся в `ACCEPTED` без события. Повтор запроса с тем же `Idempotency-Key` возвращает существующий платёж и событие не переопубликовывает. Дыра воспроизводится в упражнении шага 9 и устраняется outbox.

### 2. Тип сообщения (D6)

`PaymentRequested` — **event** (факт: платёж принят и записан), не command. Получатель proxy неизвестен; реакцию определяют подписчики (сейчас wallet).

### 3. Топики (D8)

Топик на сервис-владельца. Каждое событие имеет одного владельца.

| Топик | Владелец | События (примеры) |
|---|---|---|
| `payment.events.v1` | `t-proxy-service` | `PaymentRequested` |
| `wallet.events.v1` | `t-wallet-service` | `FundsReserved`, `FundsReservationFailed`, `FundsCaptured`, `FundsReleased` |
| `partner.events.v1` | `t-rest-service` | `PartnerPaymentSucceeded`, `PartnerPaymentFailed`, исход «неизвестен» (таймаут) |

Суффикс `v1` — версия схемы. Proxy подписывается на `wallet.events.v1` и `partner.events.v1` для обновления статуса.

### 4. Ключ партиционирования

`paymentId` (подтверждено для `payment.events.v1`; для `wallet.events.v1` и `partner.events.v1` предлагается тот же ключ, чтобы события одного платежа читались по порядку внутри каждого топика). Порядок между топиками не гарантирован, это учтено в модели статусов proxy.

**Пересмотр:** ключ `paymentId` не даёт порядка по кошельку (два платежа одного клиента могут обрабатываться wallet параллельно). Гонка за баланс закрывается в wallet оптимистичной блокировкой; ключ пересматриваем при проектировании wallet (тема №2).

### 5. Envelope и формат

JSON для старта; envelope содержит `eventId`, `correlationId` (равен `paymentId`), `causationId`, `occurredAt`, `type`, `version`. Классы envelope живут внутри каждого сервиса, без общей библиотеки (до появления реальной потребности).

### 6. Входящие события и статус в proxy

- Итоговый статус платежа proxy выводит сам из событий wallet и rest-service (D3); `PaymentCompleted` и `PaymentFailed` как события не публикуются.
- Переходы статусов монотонны: допускаются «прыжки вперёд», терминальные статусы поглощающие, опоздавшее или дублирующее событие игнорируется. Применение — один условный UPDATE.
- Событие по неизвестному `paymentId` **игнорируется с записью в лог** (до этапа 3; затем отправка в DLT) (D9).

## Рассмотренные альтернативы

| Вопрос | Вариант | Почему не выбран |
|---|---|---|
| Dual write | Outbox сразу | Правильно, но убирает «боль до лекарства» и переносит этап 3 вперёд |
| Dual write | Kafka-first | Возможен `202` на платёж, которого нет в БД |
| Тип сообщения | Command `RequestPayment` | Привязывает proxy к конкретному получателю |
| Топики | Общий топик всех сервисов | Смешивает владельцев событий, нарушает принцип «один владелец» |
| Ключ | `walletId` | Proxy не знает кошелёк; ломает порядок событий платежа |

## Последствия

- Proxy зависит от семантики saga (какое событие считать финалом); связность пересматриваем на этапе 4.
- Proxy читает несколько топиков, порядок между ними не гарантирован.
- Если никто не отреагировал на `PaymentRequested`, платёж остаётся в `ACCEPTED`; это ловится таймаутами и reconciliation (этап 4).
- Неизвестные события пока теряются из read model (только лог), что станет предметом этапа 3 (DLT).
