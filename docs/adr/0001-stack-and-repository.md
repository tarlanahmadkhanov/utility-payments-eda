# ADR-0001: стек и структура репозитория

- Статус: принято
- Дата: 2026-11-22
- Область: весь проект Utility Payments EDA (первым применяется в `t-proxy-service`)

## Контекст

Нужно зафиксировать сборку, доступ к БД и структуру монорепо до создания скелетов сервисов. Проект учебный, но решения должны быть сквозными для трёх сервисов (`t-proxy-service`, `t-rest-service`, `t-wallet-service`) и модуля нагрузочных тестов.

## Решение

1. **Язык и фреймворк:** Java 21, Spring Boot 4.x (на момент принятия решения 4.2.0). Java 21 задаётся через Gradle toolchain; автоскачивание JDK (foojay-resolver) не используем, JDK 21 должен быть установлен локально.
2. **Сборка:** Gradle с Kotlin DSL. Общая конфигурация сервисов (Java 21, Spring Boot, jOOQ, Flyway, тесты, Testcontainers) выносится в convention plugins в каталоге `build-logic`.
3. **Доступ к БД:** jOOQ (open-source edition) + Flyway. JPA не используем.
4. **Генерация jOOQ:** из схемы реального Postgres. Gradle-таска поднимает PostgreSQL в Docker, применяет миграции Flyway и запускает jOOQ codegen. Генерация привязана к каталогу миграций, поэтому не перезапускается, пока миграции не менялись. Конкретный плагин (готовый плагин для схемы «Docker + Flyway + jOOQ» или собственная таска) выбираем при настройке шага 1 плана и проверяем по актуальной документации.
5. **Версия Postgres:** 18 (образ `postgres:18`); одна и та же major-версия для codegen, Testcontainers и compose. Локальная инфраструктура: Kafka (`apache/kafka`, KRaft, один узел) и Postgres в `deploy/compose/docker-compose.yml`.
6. **Тесты:** JUnit 5, Testcontainers (Postgres, Kafka), WireMock для внешних партнёров.
7. **Структура репозитория:** монорепо, как в `Utility Payments EDA.md` (раздел 9): `services/`, `libs/` (только при реальной необходимости), `deploy/`, `docs/`, `tools/`. Сервисы не импортируют код друг друга; общий контракт — события и OpenAPI.
8. **Внешний контракт:** OpenAPI, contract-first; интерфейсы контроллеров генерируются в сборке.

## Рассмотренные альтернативы

| Решение | Вариант | Почему не выбран |
|---|---|---|
| Сборка | Maven | Общая конфигурация трёх сервисов через parent POM громоздче; нет нативных up-to-date проверок для codegen по входам |
| Доступ к БД | JPA/Hibernate | Entity-аннотации загрязняют домен; условные UPDATE, `ON CONFLICT` и `FOR UPDATE SKIP LOCKED` (outbox, идемпотентность) выражаются явным SQL нагляднее |
| Codegen | DDLDatabase (без Docker) | Быстрее, но парсер может не разбирать специфику Postgres; оставлен как **запасной путь**, решение вернуться к нему отложено |

## Последствия

- Docker обязателен на машине разработки и в CI для генерации jOOQ.
- Нужно следить, чтобы версия Postgres совпадала во всех окружениях сборки и тестов.
- Маппинг jOOQ Record → доменный объект пишется вручную в слое `adapter/persistence`.
- Optimistic locking (важно для `t-wallet-service`) реализуется явно через `WHERE version = ?` с проверкой числа затронутых строк.
- Запасной вариант codegen (DDLDatabase) остаётся доступным без смены сборочной системы.

## Открыто

- Конкретный плагин для codegen (шаг 4).
- Возврат к DDLDatabase, если Docker-codegen начнёт мешать.
